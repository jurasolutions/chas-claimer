# Identifiers are sealed, hashed with a key, and masked on the server

Source visits are split at import into a de-identified clinical part and an identity part (NRIC/FIN, name, phone, date of birth, address, member IDs, MCAF holder). The identity part is encrypted with AES-GCM; matching uses an HMAC of the NRIC/FIN; both keys derive (HKDF) from one `IDENTIFIER_KEY`, and stored values carry a version prefix so the key can rotate. Only the reveal route, channel sends and file exports open identity, and each writes an audit event. Until `ALLOW_REAL_IDENTIFIERS=yes` is set, imports refuse any NRIC/FIN outside the synthetic `T9` block, which turns "a data-intermediary agreement first" into a switch. We rejected plaintext identifiers in the snapshot (they would sit in D1 history and exports) and an unkeyed hash (seven digits per prefix is reversed by enumeration in seconds). Retrofitting encryption after real data arrives would need a data migration, so it is cheapest now.

Amended after ticket 01's review. Each sealed identity is bound to its row: the visit key and revision are AES-GCM additional data, so a sealed value copied to another visit or revision will not open. The development key published in `package.json` is recognised by its SHA-256 fingerprint and refused on any hostname but loopback (localhost, 127.0.0.1, [::1]), so a deploy that reuses it fails closed rather than sealing real identities under a public key. Keys are derived in the shared route spine: a route declared `identity: true` authenticates first, then gets its keys or answers 503 `identity_not_configured` before its handler runs, so no route can forget the check.

Amended after ticket 02a's review. The identity part also holds the dentist's notes and pre-authorisation references, because free-text notes routinely carry a patient's name, NRIC/FIN or phone, and a pre-authorisation reference can be traced to one patient at the insurer. That adds a fourth opener: the AI path opens a visit's notes, runs the scrubber (the visit's own known identifiers, then NRIC/FIN, phone and email patterns) and sends only the scrubbed text. It writes an audit event like the other openers. The clinical part keeps what the rules need: every CHAS card held, each policy's validity dates, and each pre-authorisation's benefit code and approval date.

Amended after ticket 11's review. The key now rotates. Stored values carry `v<n>:` for the key version that made them; `IDENTIFIER_KEY` is the current key (`IDENTIFIER_KEY_VERSION`, default 1) and `IDENTIFIER_KEY_PREVIOUS` is version n−1, set only during a rotation. Opening picks the key by prefix, and an unknown version fails closed. A reviewer-only, batched reseal moves rows to the current version and writes one audit event per batch; a revision may be re-keyed but its content never changed (the trigger in migration 0002 enforces it). Some hashes can't move because their plaintext is never stored (a payment statement's file hash, an unmatched statement line's patient hash): each carries the key version that made it, the reseal reports them as "can't move", and an upload that looks like a statement hashed under a retired key needs a reviewer's confirmation, audited. Finish one rotation before starting the next.
